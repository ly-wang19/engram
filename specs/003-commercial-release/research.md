# 研究决策：Engram 0.1.0 商业交付版

## 决策 1：商业化边界采用“单节点自托管 0.1.0”

**Decision**: 本阶段交付可付费授权、可自托管、可支持的单节点版本，公开状态从 alpha 调整为 0.1.0 beta/self-hosted release。

**Rationale**: 当前已有完整记忆主链和持久化，但没有多区域 HA、监管认证、企业 SSO 和云计费证据。明确边界能真正交付，同时避免把未来能力写成现状。

**Alternatives considered**: 直接标记“企业级 GA”会制造无法验收的承诺；继续停留 alpha 又不能表达本次交付收束。

## 决策 2：新命名空间使用摘要目录，旧合法目录受限兼容

**Decision**: 对原始命名空间生成有限可读前缀并附加 SHA-256 摘要；路径创建后再次用真实路径校验其位于数据根目录内。旧路径只在原始 ID 本身符合安全旧格式时回退。

**Rationale**: 现有“删除不安全字符”的方式会让不同 ID 碰撞，并允许 `..` 指向数据根目录外。摘要映射同时解决路径穿越、Unicode/规范化碰撞和超长文件名问题。

**Alternatives considered**: 只用白名单并拒绝 Unicode 会降低接入兼容；只做 URL 编码仍需处理长度与平台差异；随机 UUID 会失去确定性并需要额外索引。

## 决策 3：静态密钥映射继续作为 0.1.0 鉴权边界

**Decision**: 保留 `tenant:key` 环境配置，但严格校验；支持同租户多密钥轮换，拒绝空值和冲突映射，比较密钥时使用常量时间比较。

**Rationale**: 单节点自托管可由客户现有网关和秘密管理系统注入环境变量。无需在 0.1.0 内引入账户数据库，同时能形成清晰、可测的失败关闭边界。

**Alternatives considered**: 立即建设 OAuth/OIDC、RBAC 和密钥数据库会扩大范围，并不替代边界网关；继续允许任意 Bearer 自动创建租户只适合显式开发模式。

## 决策 4：分离 liveness 与 readiness

**Decision**: `/health` 始终提供无敏感信息的进程诊断；`/ready` 只有在鉴权已启用或显式开发开放、数据目录可写且服务初始化成功时返回 2xx。

**Rationale**: 生产编排需要区分“进程活着”和“可接收客户流量”。无鉴权的进程若被标记 ready，可能被负载均衡器直接暴露。

**Alternatives considered**: 让 `/health` 直接返回 503 会削弱排障；只在文档里提醒无法防止误配置。

## 决策 5：应用内做基础请求边界，网关负责互联网边界

**Decision**: 服务检查请求体上限和字段上限，返回 413/422；TLS、WAF、分布式速率限制和 IP 策略由反向代理/API 网关承担并在文档中列为生产必需。

**Rationale**: 应用必须防止明显的单请求资源滥用，但在单进程内实现“分布式限流”会给出虚假安全感。

**Alternatives considered**: 完全依赖网关会让误部署风险过高；引入 Redis 限流会破坏轻量单节点交付和零依赖原则。

## 决策 6：标准容器采用非 root、多阶段、持久卷、安全默认

**Decision**: 前端在 Node 构建阶段编译，Python 运行阶段只保留运行产物；使用非 root 用户和 `/data` 卷，不设置 `ENGRAM_OPEN` 默认值，Compose 从显式 `.env` 读取密钥。

**Rationale**: 容器是最容易复现的商业交付形态，能够把 UI、服务和运行依赖固定在同一产物内。

**Alternatives considered**: 只提供 systemd 会绑定机器路径；默认开放容器便于试玩但不适合商业交付。

## 决策 7：统一 0.1.0 版本并保留 beta 诚实状态

**Decision**: Python 包、服务 OpenAPI、TypeScript SDK、前端和持久化 manifest 统一为 0.1.0；开发状态使用 Beta，不使用 Production/Stable 分类。

**Rationale**: 统一版本是升级、支持和漏洞响应的基础。Beta 表示可供外部真实使用，同时不虚构尚未完成的企业能力。

**Alternatives considered**: 继续 0.0.1 与服务 0.1.0 漂移会让客户无法判断升级；直接 1.0.0/Stable 缺少长期兼容性和规模证据。

## 决策 8：本次不重跑 500 题算法实验

**Decision**: 0.1.0 发布只做工程和产品验收，不修改检索/抽取/排序算法，不生成新算法结论；既有公开数字继续由原始 500 题日志支撑。

**Rationale**: 500 题实验成本高，且本次没有算法干预变量。把发布工程测试与算法提升实验分开，符合“测量后宣称”的原则。

**Alternatives considered**: 为了仪式感重跑 500 会浪费资源且引入模型方差；完全不跑测试则无法证明交付可靠。
